# Separate audit storage status (Day 2)

PRD v2.1 `DR-09` requires audit storage separate from the operational database. Four independent Neon projects now exist: operational development/staging from Day 1 and audit development/staging created on Day 2. Audit project IDs are `aged-surf-42976367` (development) and `lucky-shadow-22569401` (staging). `audit_event` DDL was applied to both audit projects with `classroom_id` nullable for platform actions.

The Neon UI's ordinary **Add role** produced `paireval_audit_runtime` with inherited `neon_superuser` membership. A PostgreSQL privilege query showed that this role still had `UPDATE` and `DELETE` despite an explicit table `REVOKE`; it must never be used by the application. The runtime uses a separate SQL-created role, `paireval_audit_app`, with no `neon_superuser` membership, no role/database creation, no RLS bypass, and grants limited to schema `USAGE` and table `SELECT, INSERT`. Its credentials are generated locally into ignored environment files. `scripts/audit-smoke.mjs` connected as this role to each database and confirmed that `INSERT/SELECT` succeed while actual `UPDATE/DELETE/TRUNCATE` attempts fail with PostgreSQL `42501`; the synthetic event was rolled back. `src/lib/full-system-audit.ts` also checks the connected role and effective table privileges before any write.
