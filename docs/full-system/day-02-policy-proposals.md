# Day 2 policy proposals — provisional, not approved

These are concrete decisions for the Privacy Officer, academic owner, and security/operations owner to review. They do not amend PRD v2.1 and must not be treated as consent, production authorization, or an acceptance result. Staging remains synthetic-only until the owners record a decision, name, date, and evidence.

## P-PRIV-01 — versioned notice and first login

**Proposed notice version:** `2026-09-paireval-v1`. Show it immediately after a verified Google callback and before any classroom data. Record user ID, exact notice version, and UTC acceptance time. Denial or no response leaves classroom APIs at `PRIVACY_NOTICE_REQUIRED`; revocation disables further access pending an approved handling process. A version change requires renewed acknowledgement. `synthetic-staging-v1` in the current code is a development sentinel, not approved notice text or consent.

**Proposed text for owner review:** “PairEval uses your university email to sign in and match your class roster; your name and optional student ID to support class administration; submitted comparisons, revisions, and evaluator identity to calculate scores and investigate academic integrity; and security/audit records containing action, time, account, resource, IP where available, and reason. Students see their own permitted aggregate results only after the anonymity threshold and never see evaluator identity. Co-teachers see pseudonyms; only an authorized Owner may reveal evaluator identity, and each reveal is audited. System administrators can manage access but routine use does not expose evaluator identity. The PRD specifies two academic years for email, name, optional student ID, evaluation results and evaluator identity; time-on-task is disabled for real users until OQ-6 is decided, with one academic year proposed by the PRD if enabled. After retention, identifying fields are anonymized while aggregate statistics remain. Contact the designated data controller to request a copy of your data; the PRD sets a 30-day response target.”

**Approval gates:** Confirm the data controller/contact, lawful basis and whether acknowledgement is legally appropriate, exact definition of “academic year” and start date, backup/audit retention, identity access roles, data-subject workflow, and OQ-6. No real-user notice or acceptance endpoint is enabled from this draft.

## P-AUDIT-01 — outcomes and failure semantics

**Proposed design:** Keep a separately stored immutable `*_REQUESTED` event before each critical mutation. Write a correlated outcome record (`*_COMMITTED` or `*_REJECTED`) to the separate audit database. Put the outcome payload in a transactional operational outbox in the same PostgreSQL transaction as the domain change. A retry worker copies outbox entries idempotently to audit storage; it must use the restricted `paireval_audit_app` credential and alert on age/backlog. The outbox is a delivery queue, not the authoritative audit history. An intent without a matching outcome is `UNRESOLVED`, never evidence of a committed change.

**Provisional implementation choice:** Migration `003_audit_outbox.sql` creates only the operational delivery queue and has been applied to PairEval development and staging. `runAuditedMutation` writes the request event after authorization checks, queues `*_COMMITTED` before the domain transaction commits, and then attempts delivery to the separate audit database. A rolled-back mutation queues `*_REJECTED` after rollback. Both outcomes use the same request ID as the intent and a fixed event ID so retries cannot create duplicate rows. Staging verified 5 correlated committed and 1 rejected outcome with zero pending rows. `audit-outbox-drain.mjs` is a manual recovery path; scheduling, alert threshold and independent operator ownership still need Security/Operations approval. These synthetic tests are not production policy approval.

**Proposed failure rule:** If the pre-mutation audit intent cannot be stored, abort the operation. If the operational transaction rolls back, append `*_REJECTED` with a safe reason category. If the commit succeeds but outcome delivery is delayed, return an explicit pending operation status and correlation ID, prevent blind client retries, and alert operations. Do not report success as fully audited until the outcome is present. This response contract and maximum tolerated delay need Product/Security approval before real-user acceptance. The prototype covers the current classroom, roster, role and entitlement mutations, not the PRD's later publish/score/export/identity events.

**Pending response prototype:** A committed operational change whose audit delivery is delayed returns HTTP `202`, `{data:{status:"AUDIT_PENDING",requestId}}`, and `Retry-After: 5`; the client must not repeat the mutation. A transaction commit with an uncertain acknowledgement returns `202` with `COMMIT_UNKNOWN`, since the domain result cannot be asserted. Neither response implies audit success. Product must approve a read-only status lookup and user-facing wording before real users rely on it. Until then, exercise this path with synthetic data only.

**Required event coverage:** Publish/unpublish, pair regeneration, score override, finalize/reopen, identity-bearing export, each evaluator identity view, and each role change per `FR-AUDIT-01`. Each event must have actor, action, resource, before/after, UTC time, trusted IP when available, and mandatory reason where specified by `FR-AUDIT-02`. The current prototype covers request intents and correlated outcomes for selected classroom, roster, role, and entitlement mutations only.

## P-AUDIT-02 — integrity, retention, and backup

**Proposed integrity control:** A daily, ordered SHA-256 checkpoint over all audit events through a high-water mark, with the backup digest and manifest copied to a separately administered, immutable store. Alert on mismatch, missing checkpoint, or unresolved request/outcome pair. `scripts/audit-integrity.mjs` is a development aid: it creates an ignored local NDJSON export and manifest, then compares the saved prefix to the live separate audit database. It does not provide independently controlled storage or prove resilience against an audit database owner plus local-file compromise.

**Proposed retention and recovery:** Keep identifiable audit records for two academic years after the class term ends, subject to appeal/incident hold; then anonymize identity references under an approved method that preserves chain verifiability. Export encrypted daily backups to a separate account, retain daily copies for 30 days and monthly copies for two academic years, and run a quarterly restore into a clean isolated database with row-count/digest comparison. These numbers are a proposed operational rule, not in the PRD audit section. The Privacy Officer must reconcile them with PRD §14.1, storage cost, legal holds, and the “append-only” rule before any retention job or destructive restore is implemented. `scripts/audit-restore-test.mjs` exercises a one-row synthetic restore into a temporary table in a transaction that rolls back; it is evidence of backup-format readability, not a complete disaster-recovery drill.

**Owners needed:** Privacy Officer (notice, retention, anonymization, OQ-6), academic/Product owner (pending outcome UX, evaluator identity access), Security/Operations owner (backup account, manifest signing/key custody, alerts, restore tests). Until approved, keep only synthetic staging data and mark `FR-PRIV-01`, `FR-AUDIT-01–03`, and `DR-09` incomplete.
